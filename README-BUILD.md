  (`const FIREBASE_CONFIG`, line 103) by script and injected into all three pages with a
  placeholder swap. It was never printed into the transcript. All other config fields match
  the brief.
- `wallet-fb.html` is generated by `build-wallet-fb.py` (assert-first, write-once). It makes
  exactly two changes to the original wallet:
  1. removes `<link rel="stylesheet" href="./__fragment.css">` (that file only exists on the

  2. injects the gate (`<style>`, overlay `<div>`, Firebase SDK tags, gate script) right after
     `<body>`, plus the "client-side gate only" comment at the top of the file.
  The wallet's own JS is untouched.
- Helper scripts live outside this folder (so they never get uploaded to the public site):
  `/data/work/datastar-pro--tp97/tmp/sevia-build/` — `build-wallet-fb.py`, `inject-key.py`,

## Behaviour decisions

- Visitor id: `localStorage['seviaFbDoor']`, random UUID with dashes stripped.
- On load the door reads the row, creates it only if missing (status `pending`, `opens: 1`),
  otherwise merges `{opens: increment(1), last_seen}` — `status` is never sent on an update.
  First visit therefore shows "Opened 1 time" (a double-count bug found and fixed in testing).
- Polling is a 3 s `get()` loop rather than `onSnapshot`: it matches the fragment's cadence,
  survives listener failures, and keeps the door page trivial. The keeper console does use
  `onSnapshot`.
- Pledge: writes `{who, pledge}` first, then rings ntfy only if the row's `notified` flag is
  false, and sets `notified: true` only after a 2xx response. One ring per visitor.
- Approved visitors are sent to `./wallet-fb.html` **without** a token in the URL (the gate
  reads localStorage). This deliberately prevents an approved visitor from sharing a working
  link with someone who was never approved.
- If Firestore is unreachable the door shows the waiting room with "The door is slow to
  answer — retrying…" instead of a dead spinner; the keeper list explains that the rules may
  not be published yet.

## Deviations from the brief (all deliberate)

1. **ntfy Title is ASCII**: `Someone is at the Sevia door` (no 🚪). Chromium throws
   `TypeError` for non-Latin-1 characters in a `fetch` header value — verified in the test
   browser. Body, `Priority: high` and `Tags: door` are as specified.
2. **Email + password fallback on the keeper page**, behind a small link. The management page
   uses email/password, so that provider is definitely enabled; Google may not be. Google
   popup remains the primary path.
3. **Sign-out control** added at the bottom of the phone-alerts card (the fragment console had
   none).
4. **Client-side sort** in the keeper list instead of `orderBy('last_seen')`, so a row whose
   server timestamp is still resolving can never drop out of the list.
5. **Counts line** ("3 visitors · 2 waiting · 1 in · 0 shut out") and the **phone-alert topic
   card** (with copy button) added to the keeper page; the fragment's "ring this phone" card
   used fragment push, which does not exist here.
6. **Wallet gate extras**: "This wallet opens from the door" + a link back when there is no
   visitor id, a retry note while Firestore is unreachable, and a two-poll grace period before
   an unknown visitor is told "Not available right now." (avoids a flash for a row that is
   still being created).
7. **Rules delivered as a snippet, not a full ruleset.** The project already has rules for the
   frozen-foods collections, and I could not read them, so a full replacement could break the
   management app. The guide tells the owner to copy the existing rules to a note first, paste
   the block above the last two closing braces, publish, then sanity-check the management page.
   *If the parent prefers the one-paste full-file flow: get a screenshot of the current Rules
   page and merge this block into it.* Note that Firestore ORs all matching rules — if the
   existing ruleset contains a broad `match /{document=**}` allow for signed-in users, staff
   accounts could also change visitor statuses, so a strict full ruleset is the better end
   state once the current text is known.

## Known limits to state honestly

- The wallet cover is **client-side only** — a friendly door, not a security boundary; the file
  says so at the top and the guide repeats it.
- The visitor list is world-readable by design (anonymous door); it holds only names people
  typed plus counters.
- An approved visitor stays unlocked for that browser session even if later blocked.
